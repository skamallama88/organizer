# Planning and execution are separate ItemProcessor stages

Organizer separates rule evaluation from filesystem mutation through the `ItemProcessor` module. Planning produces an immutable execution plan that can be previewed by the CLI and web UI; execution consumes that plan in apply or dry-run mode. This keeps watcher, scanner, CLI, and web callers on one deep module while preventing preview behavior from becoming a second implementation of rule and action semantics. Supported file and folder copies preserve contents, basenames, and POSIX mode bits; every execution report exposes a non-fatal warning that ownership, ACLs, extended attributes, and platform-specific metadata are not guaranteed. Archive actions use the same seam: planning resolves the archive output name by removing at most one final `.zip`, `.7z`, or `.rar` suffix case-insensitively, preserving all other suffixes, then appending the requested `.zip` or `.7z` extension; execution creates a private staged ZIP or 7z archive, validates source consistency, publishes it without overwriting, and removes the source only when `preserve_original` is false. Unarchive preview inspects archive metadata only; execution validates each entry, stages all content, publishes one extraction root without overwriting, and suppresses corrupt, protected, traversal, resource-limit, and unavailable-tooling failures while retaining the source. Unarchive execution supports nested extraction: archives discovered within the staged extraction tree are extracted in place up to a configured `max_depth`, with the nested archive preserved within its extraction root and deeper archives left for independent discovery. Cross-watch move and copy actions carry a processing lineage: the planner rejects plans that would return an item to a watch folder already in its lineage, records the resulting-path handoff to each newly entered watch, and persists the lineage with the processing attempt.
